## 1. O que este submódulo faz

> **Uma frase:** o S4.3 apaga sozinho as evidências de vídeo que passaram do prazo da LGPD (7 dias) ou, numa emergência de disco (NVMe a 85%), as mais antigas primeiro — nunca as travadas para auditoria.

O professor resume o motivo: *"retenção que depende de alguém lembrar de apagar não é retenção, é acúmulo"*. São duas motivações que se reforçam: o disco finito da Jetson e a minimização de dados pessoais exigida pela LGPD.

| Não faz | Quem faz |
|---|---|
| Gravar o `.mp4` e o registro no SQLite | S4.2 — Binding Evento-Mídia |
| Travar/destravar um clipe para auditoria | Regra de auditoria RBAC/LGPD (Davi) — o S4.3 só **respeita** a trava |
| Expor o estado do clipe na API | S4.4 — o DTO já devolve `is_retained` |

## 2. Entradas, processamento e saídas

### 2.1 O que entra

| Entrada (guia) | De onde vem | Como chega no código |
|---|---|---|
| **Estado de ocupação do NVMe** | `statvfs(2)` no diretório de mídias | `StatvfsDiskUsageProvider` → `DiskUsage {usedBytes, availableBytes}` (mesma conta do `df`) |
| **Sinalizador `is_locked_for_audit`** | Tabela `media_clips` do SQLite (S4.2) | `IMediaClipRepository::findPurgeCandidates()` + releitura com `findById()` antes de apagar |
| Data de criação e tipo de cada mídia | `created_at_ms` e extensão do `file_path` | `MediaClip::createdAt()`, `media_kind_of()` |
| Relógio | Sistema | `IClock` (os testes usam um relógio falso) |

### 2.2 O que faz

A cada varredura, o `PurgeMediaUseCase`:

1. lê os candidatos (clipes com `is_retained = 1` e `is_locked_for_audit = 0`) e mede o tamanho de cada arquivo;
2. aplica as estratégias **em ordem** — cada uma recebe o disco medido **depois** da anterior:
   1. `LgpdRetentionStrategy`: seleciona tudo com idade ≥ prazo do seu tipo (clipe ou snapshot);
   2. `DiskQuotaFifoStrategy`: se o disco está ≥ 85%, seleciona do mais antigo para o mais novo até a projeção cair abaixo de 80%;
3. para cada selecionado: **relê** a trava de auditoria → apaga o arquivo → `is_retained = false` no SQLite → anexa uma linha no log.

### 2.3 O que sai

| Saída (guia) | Onde | Formato |
|---|---|---|
| **Liberação de espaço no NVMe** | Diretório de mídias | Arquivo `.mp4`/`.jpg` removido |
| **Update SQLite** | `media_clips.is_retained = 0` | O registro **fica** (o evento continua dizendo que teve mídia); `GET /api/v1/clips/{id}` passa a responder `"is_retained": false` |
| **Log de Expurgo** | `s4_purge_log.jsonl`, ao lado do banco | Uma linha JSON por mídia (exemplo abaixo) |
| Relatório da varredura | `PurgeReport` (retorno do caso de uso) | Expurgados, falhas, ocupação antes/depois; o daemon imprime um resumo `[S4.3]` no stderr |
| Alerta de disco sem saída | `DiskQuotaExceededError` | Disco ≥ gatilho e nada apagável → `[S4.3] ALERT: ...` no stderr |

```json
{"purged_at":"2026-09-29T15:49:44.146Z","clip_id":"clip-fe6b...","event_id":"evt-smoke-1",
 "file_path":"/data/media/evt-smoke-1.mp4","reason":"lgpd_retention_expired",
 "file":"deleted","bytes_freed":37200,"disk_used_ratio":0.8237}
```

`reason`: `lgpd_retention_expired` ou `disk_quota_fifo`. `file`: `deleted`, `already_missing` (arquivo já não existia) ou `kept_for_other_clip` (outro clipe retido usa o mesmo arquivo — ver §5.4).

## 3. Quando roda (frequência — tópico de discussão do guia)

O `PurgeDaemon` é uma thread com **duas cadências**, porque as duas regras envelhecem em ritmos diferentes:

| Gatilho | Padrão | Por quê |
|---|---|---|
| Ao iniciar o serviço | sempre | Recupera o atraso de quando o serviço estava parado |
| Varredura completa periódica | a cada **1 h** (`--sweep-interval`) | O prazo LGPD é medido em dias; de hora em hora sobra |
| Checagem de disco | `statvfs` a cada **30 s** (`--disk-check-interval`) | Várias aplicações gravando podem encher o disco em minutos. Acima do gatilho, a varredura roda **na hora**, sem esperar a hora cheia. Um `statvfs` custa microssegundos e não toca o disco |
| Sob demanda | `PurgeDaemon::requestSweep()` | Gatilho por evento de I/O (ex.: o S4.2 acabou de gravar um clipe) |

Nenhuma exceção derruba a thread: falha vira linha `[S4.3]` no stderr e a próxima varredura tenta de novo.

## 4. Política FIFO de emergência (tópico de discussão do guia)

* **Gatilho 85%, alvo 80%** (`--quota-trigger`, `--quota-target`). Com gatilho = alvo, cada clipe novo empurraria o disco de volta acima do limite e cada varredura apagaria uma mídia por vez, para sempre; a folga de 5 pontos faz o expurgo abrir espaço de uma vez. Gatilho = alvo continua permitido para quem quiser apagar o mínimo possível.
* **Mais antigo primeiro** (`created_at`), pulando mídia travada ou já expurgada.
* **LGPD antes da cota:** o que já venceu sai primeiro; a cota só toca em mídia dentro do prazo se ainda faltar espaço.
* **Sem saída:** se o disco está no gatilho e não há nada apagável (tudo travado, ou o disco foi tomado por outro serviço), a estratégia lança `DiskQuotaExceededError` — nenhuma regra de retenção resolve, e alguém precisa ser avisado.

A ocupação é medida como o `df` a mostra (usado ÷ (usado + disponível), sem a reserva do root), então "85%" no S4.3 é o mesmo número que o operador vê na Jetson.

## 5. Decisões de projeto

### 5.1 Strategy (GoF), como pede o guia

`IRetentionStrategy` só **decide** (domínio puro, sem I/O). Apagar arquivo e atualizar o banco é do `PurgeMediaUseCase`. Uma regra nova (ex.: prazo por aplicação) é uma classe nova, sem tocar no caso de uso.

> O contrato `IRetentionStrategy` que já existia recebia só a lista de clipes. As regras precisam também de "agora" e da ocupação do disco, então ele passou a receber um `RetentionContext {now, diskUsage}` e candidatos com tamanho (`PurgeCandidate`). Não havia nenhum uso do contrato antigo no repositório.

### 5.2 Ordem das operações sobrevive a queda

Arquivo primeiro, banco depois. Se o processo cair no meio, a próxima varredura encontra o registro sem arquivo e só conclui o resto (`file: already_missing`). Na ordem inversa sobraria um arquivo que nenhum registro aponta — mídia órfã que nunca mais seria apagada.

### 5.3 A trava de auditoria é relida imediatamente antes de apagar

Entre a consulta de candidatos e a exclusão, alguém pode travar o clipe para auditoria. Evidência travada nunca some, então o registro é relido (`findById`) antes de cada exclusão.

### 5.4 Arquivo compartilhado entre clipes

O S4.2 nomeia o arquivo pelo `event_id` (`<media_dir>/<event_id>.mp4`). O mesmo evento enviado duas vezes — e o `event-demo` a cada reinício do daemon demo — gera **dois clipes apontando para um arquivo**. Apagar pelo clipe antigo destruiria a mídia do novo, que pode estar travado. O S4.3 marca o antigo como expurgado mas **mantém o arquivo** (`kept_for_other_clip`) enquanto houver outro clipe retido com o mesmo caminho. A correção de raiz é o S4.2 gerar nomes únicos por clipe.

### 5.5 Log em JSON Lines, não no SQLite

Uma tabela no mesmo banco exigiria uma segunda conexão escrevendo em paralelo com o S4.2, e uma escrita do daemon na hora errada devolveria `SQLITE_BUSY` para o `POST /api/v1/events`. Um arquivo próprio não disputa trava com ninguém, é só anexado, pode ser rotacionado (`logrotate`) e `grep`/`jq` bastam para auditar.

### 5.6 Prazo por tipo de mídia

A atividade pede "por quanto tempo **cada tipo** de mídia é guardado". `RetentionPolicy` tem um prazo para clipe e outro para snapshot (`.jpg`/`.jpeg`/`.png`), ambos 7 dias por padrão. A idade conta a partir de `created_at`; com exatamente 7 dias o clipe já está vencido.

## 7. Como usar

O `main.cpp` já liga o daemon. Parâmetros (todos opcionais):

```bash
./s4_media_evidence --port 8080 --db /data/s4.db --media-dir /data/media \
    --retention-days 7 --quota-trigger 0.85 --quota-target 0.80 \
    --sweep-interval 3600 --disk-check-interval 30 \
    --purge-log /data/s4_purge_log.jsonl   # padrão: ao lado do --db
```

Demonstração rápida (prazo de ~8,6 s):

```bash
./s4_media_evidence --port 18080 --db /tmp/s4/s4.db --media-dir /tmp/s4/media \
    --retention-days 0.0001 --sweep-interval 2 --disk-check-interval 1 &
curl -X POST http://127.0.0.1:18080/api/v1/events -d '{"event_id":"evt-1"}'
sleep 12
curl http://127.0.0.1:18080/api/v1/clips/<clip_id>   # "is_retained": false
cat /tmp/s4/s4_purge_log.jsonl
```

Montagem em código (outra build de aplicação):

```cpp
auto disk = std::make_shared<infrastructure::StatvfsDiskUsageProvider>(mediaDir);
const domain::QuotaPolicy quota(0.85, 0.80);
auto purgeMedia = std::make_shared<application::PurgeMediaUseCase>(
    repository, fileStorage, disk,
    std::make_shared<infrastructure::JsonLinesPurgeLog>("/data/s4_purge_log.jsonl"),
    std::make_shared<infrastructure::SystemClock>(),
    std::vector<std::shared_ptr<const domain::IRetentionStrategy>>{
        std::make_shared<domain::LgpdRetentionStrategy>(domain::RetentionPolicy()),
        std::make_shared<domain::DiskQuotaFifoStrategy>(quota)});

infrastructure::PurgeDaemon daemon(purgeMedia, disk, quota);
daemon.start();          // varre já, depois a cada 1 h e sempre que o disco passar de 85%
daemon.requestSweep();   // opcional: logo após gravar um clipe
daemon.stop();           // espera a varredura em curso terminar
```
