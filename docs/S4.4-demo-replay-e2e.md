# S4 — Demonstração do fluxo de evidência de mídia

Guia para **mostrar o S4 funcionando** para outra pessoa, do vídeo real até o
artefato indexado. Cada passo traz o comando, o que esperar na saída e por que
aquele resultado é a prova de que a etapa funcionou.

O fluxo inteiro, em uma linha:

```
MP4 de teste → ring buffer em RAM → evento → janela [T−1s, T+0.5s] → MP4 muxado → SHA-256 → API
```

Estimativa: 5 minutos se o build já estiver pronto, 15 minutos do zero.

---

## Antes de começar

Você precisa de:

- **CMake 3.20+**, compilador C++20, `sqlite3`, OpenSSL
- **GStreamer 1.0 com os plugins certos** — este é o passo que mais trava gente:

```bash
# Debian / Ubuntu
sudo apt-get install gstreamer1.0-dev libgstreamer-plugins-base1.0-dev \
    gstreamer1.0-plugins-base gstreamer1.0-plugins-good \
    gstreamer1.0-plugins-bad gstreamer1.0-plugins-ugly \
    gstreamer1.0-libav gstreamer1.0-tools

# Fedora / RHEL
sudo dnf install gstreamer1-devel gstreamer1-plugins-base-devel \
    gstreamer1-plugins-base gstreamer1-plugins-bad gstreamer1-plugins-ugly \
    gstreamer1-libav
```

> **Por que `plugins-bad` e obrigatório aqui, apesar do nome:**
> o `h264parse` — o elemento que converte o sample do demuxer em *access unit*
> alinhada, que é o formato que o ring buffer assume — mora em
> `libgstvideoparsersbad.so`, ou seja, no conjunto *bad*. Não está em *base*
> nem em *good*. Sem ele o `cmake` acha o GStreamer, compila tudo, e a falha
> só aparece na hora de montar o pipeline:
> `no element "h264parse"`.
>
> E `libgstreamer-plugins-base1.0-dev` (e não `gstreamer1.0-dev`) é quem
> instala o `gstreamer-app-1.0.pc`, usado para achar `gstappsrc`/`gstappsink`.
>
> `plugins-ugly` e `libav` são para **provar**, não para compilar: é onde moram
> o `x264enc` e o `avdec_h264`. Sem eles a suíte de captura real sai como
> *Skipped* e o passo 4 abaixo não decodifica pixels — o script avisa qual dos
> dois está faltando em vez de fingir que verificou.

Confira antes de seguir:

```bash
gst-inspect-1.0 h264parse >/dev/null && echo "h264parse ok"
gst-inspect-1.0 qtdemux  >/dev/null && echo "qtdemux ok"
gst-inspect-1.0 avdec_h264 >/dev/null && echo "avdec_h264 ok (pixels serao verificados)"
pkg-config --exists gstreamer-app-1.0 && echo "gstreamer-app-1.0 ok"
```

**O Dockerfile já resolve isso sozinho.** Se você só quiser demonstrar sem
instalar nada, pule para [Opção B](#opção-b-tudo-dentro-do-docker).

## Opção A — na máquina

### Passo 0 — compilar

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j"$(nproc)"
```

A configuração deve dizer que o GStreamer foi encontrado:

```
-- GStreamer habilitado: captura e replay do S4.1
```

Se aparecer erro pedindo GStreamer, a mensagem lista o pacote exato do seu
sistema. **Não existe build silencioso sem GStreamer**: se você realmente
querer compilar sem ele, é de propósito, com `-DODS_S4_WITH_GSTREAMER=OFF`.

### Passo 1 — a suíte inteira passa

```bash
ctest --test-dir build --output-on-failure
```

```
100% tests passed, 0 tests failed out of 13
```

> O número importa, e o que importa mais é o que está **contado** dentro dele.
> São treze agora: as dez do E2E de replay mais a captura real, a retenção de
> domínio e a de runtime, que vieram do master.
>
> Duas delas podem sair como *Skipped* — e devem: `test_s4_replay_e2e` sem MP4
> em `video_test/` e `test_s4_gstreamer_capture` sem `x264enc`/`avdec_h264`.
> Um teste que não exercita o que diz exercitar não pode aparecer como
> aprovado; aparece como pulado, e o CTest diz *Skipped*. Se o build tivesse
> degradado sem GStreamer, o ctest *ainda assim* reportaria sucesso — por isso o
> `cmake` exige o GStreamer em vez de aceitar a ausência em silêncio, e por isso
> a ausência de material virou código de saída `77` em vez de `return` calado.
>
> Para que a ausência de vídeo reprove em vez de pular:
> `-DODS_S4_REQUIRE_SAMPLE_VIDEO=ON` (é o que o `Dockerfile` usa).

### Passo 2 — ver o ring buffer receber o vídeo real

Este é o passo mais importante para a demonstração, porque é onde fica
visível que o dado entra no sistema.

```bash
./build/s4_media_evidence \
  --source "video_test/10 Minutes of Amazon Rainforest (Free Download).mp4" \
  --port 8080 \
  --db /tmp/demo.db \
  --media-dir /tmp/demo-media &
```

Saída esperada:

```
S4 Media Evidence listening on http://127.0.0.1:8080/api/v1/clips/{id}
Replaying 'video_test/10 Minutes of Amazon Rainforest (Free Download).mp4' into the ring buffer
```

Agora, **enquanto o daemon roda**, pergunte ao buffer o que ele tem:

```bash
curl -s http://127.0.0.1:8080/api/v1/buffer/stats | jq
```

```json
{
  "capacity_bytes": 756000,
  "bytes_used": 722337,
  "fill_ratio": 0.955472,
  "frames_stored": 2671,
  "frames_ingested_total": 18032,
  "frames_evicted_total": 15361,
  "has_frames": true,
  "session_id": "replay-10 Minutes of Amazon Rainforest (Free Download).mp4",
  "span_seconds": 89.089,
  "oldest_capture_ts_ns": 9922820239953,
  "newest_capture_ts_ns": 10011909239953
}
```

> Os números exatos variam entre execuções — o buffer é preenchido enquanto a
> consulta acontece. O que **não** varia é a relação: os 18 032 quadros entram
> todos, e o que fica guardado é sempre uma janela curta e cheia.

O que cada linha prova, e por que apontar para ela durante a demo:

| Campo | O que demonstra |
|---|---|
| `frames_ingested_total: 18032` | O arquivo tem 18 032 quadros; **todos entraram**. |
| `frames_evicted_total: 16114` | O ring buffer é *circular* e curto: guardou ~1 900 dos 18 032, descartou o resto por falta de espaço. Isso é o ponto do S4.1. |
| `bytes_used ≈ capacity_bytes` | O buffer está cheio — está maintaining uma janela viva, não acumulando. |
| `oldest_capture_ts_ns` / `newest_capture_ts_ns` | Existe um **relógio de captura** próprio, independente do relógio de parede. É ele que permite endereçar "aquele instante do vídeo". |
| `session_id` com o nome do arquivo | A sessão distingue uma gravação de outra. Reiniciar a mesma fonte não confunde o histórico. |

E o buffer é visível no sistema de arquivos enquanto o daemon roda:

```bash
ls -lh /dev/shm/ods_s4_ring_*
```

### Passo 3 — disparar um evento e extrair o clipe

O evento é o gatilho. A janela é `[T − pre, T + post]` em torno dele.

```bash
# O instante do evento tem que estar no que o buffer realmente guarda.
# Por quê? O replay de arquivo entrega os 10 minutos em ~500 ms e depois chega
# ao fim (EOS) — e depois do fim não existe "depois" no relógio de captura.
TS=$(curl -s http://127.0.0.1:8080/api/v1/buffer/stats | jq -r .newest_capture_ts_ns)

curl -s -X POST http://127.0.0.1:8080/api/v1/events \
  -H 'Content-Type: application/json' \
  -d "{\"event_id\":\"evt-demo-1\",\"capture_ts_ns\":$TS,\"pre_window_seconds\":1.0,\"post_window_seconds\":0.5}" | jq
```

```json
{
  "clip_id": "clip-2f1a…",
  "file_uri": "/tmp/demo-media/evt-demo-1.mp4",
  "start_time": "2026-09-28T18:36:01.553Z",
  "end_time": "2026-09-28T18:36:02.553Z",
  "sha256_hash": "a6dacf4364180d06ece93953f3751311a63b34b9da324bd55bc892000ce4414c",
  "is_retained": true,
  "is_locked_for_audit": false
}
```

`start_time`/`end_time` em ISO 8601, com 1,5 s de diferença — a janela pedida.

### Passo 4 — provar que o artefato é um MP4 de verdade

**Este é o passo que separa "gerou um arquivo" de "gerou vídeo".** Um arquivo
`.mp4` com bytes H.264Annex-B dentro — que é o erro clássico — tem tamanho
plausível e abre em player nenhum. Então desmonte o container:

```bash
# O primeiro box de um MP4 válido é o ftyp (file type)
head -c 8 /tmp/demo-media/evt-demo-1.mp4 | tail -c 4    # deve imprimir: ftyp

# E o teste que vale: passar pelo demuxer e pelo parser de vídeo de verdade
gst-launch-1.0 -q filesrc location=/tmp/demo-media/evt-demo-1.mp4 \
  ! qtdemux ! h264parse ! fakesink
echo "saída: $?"        # 0 = o GStreamer aceitou ler o arquivo inteiro
```

A segunda linha é a importante. `qtdemux` monta as tabelas de amostra e
`h264parse` reparseia cada amostra; se algum box estiver corrompido, some ou
estiver fora de ordem, isso falha.

**O que essa prova não cobre:** `h264parse` faz *parse* do bitstream, não
decodifica pixels. Ele valida e separa NALs — o que já descarta o erro clássico
de "Annex-B com nome de .mp4", porque o container tem `ftyp`, `moov` e `mdat`
e as tabelas de amostra são coerentes. Para provar que os pixels decodificam,
faça falta um decoder **entre** o parse e o sink:

```bash
# decoder disponível? (vaapi, VA-API, o que o hardware oferecer)
gst-inspect-1.0 avdec_h264 >/dev/null 2>&1 && echo "avdec_h264 ok" || echo "sem decoder por software"
gst-inspect-1.0 vaapih264dec >/dev/null 2>&1 && echo "vaapih264dec ok" || echo "sem VA-API"

# com decoder presente, o pipeline completo até pixel cru
gst-launch-1.0 -q filesrc location=/tmp/demo-media/evt-demo-1.mp4 \
  ! qtdemux ! h264parse ! vaapih264dec ! videoconvert ! fakesink   # rc=0
```

> ⚠️ Em máquina **sem** decoder H.264 (a de desenvolvimento aqui não tem nem
> `avdec_h264` nem `vaapih264dec`), essa última linha não roda — e o `rc` vai
> ser 1, não 0. Não é defeito do clipe: é ausência de decoder. A verificação
> que **sempre** funciona é a do `qtdemux ! h264parse ! fakesink` acima, e é
> por isso que é ela que o `smoke_e2e.sh` usa.

### Passo 5 — o hash confere e é reprodutível

```bash
# (a) o hash publicado é o do arquivo em disco
curl -s http://127.0.0.1:8080/api/v1/clips/clip-2f1a… | jq -r .sha256_hash
sha256sum /tmp/demo-media/evt-demo-1.mp4 | cut -d' ' -f1
# devem ser idênticos
```

Agora a propriedade que faz disso ser **evidência** e não só um arquivo:

```bash
# (b) extrair DE NOVO o mesmo material produz o MESMO hash
./build/s4_media_evidence --source "video_test/10 Minutes of Amazon Rainforest (Free Download).mp4" \
  --scenario --port 0 --db /tmp/demo2.db --media-dir /tmp/demo2-media 2>&1 | grep sha256
sha256sum /tmp/demo2-media/event-demo.mp4
```

Os dois hashes são `a6dacf4364180d06…`. Isso **precisa** acontecer, e não é
grátis: o `mp4mux` do GStreamer grava a hora em que o muxing aconteceu nos
boxes de cabeçalho (`mvhd`, `tkhd`, `mdhd`). Sem tratamento, o mesmo vídeo
produz um hash diferente a cada extração, e um hash que muda sozinho não
identifica nada.

Por isso o muxer zera esses três campos depois de muxar
([`iso_bmff_timestamps.cpp`](../../src/infrastructure/media/iso_bmff_timestamps.cpp)),
**sem tocar** em `mdat` (as amostras de vídeo), nem em `timescale`/`duration`.
O valor de substituição é um sentinela obviamente não-real, e não zero: zero
significaria 1904-01-01, que é um tempo plausível e portanto uma mentira.

### Passo 6 — o mesmo hash em outra máquina

```bash
docker build --target smoke -t s4-media-evidence:smoke .
```

Esse estágio roda o `scripts/smoke_e2e.sh` contra a imagem final e falha o
build se algo estiver errado. O hash que sai de dentro do container Debian é
o mesmo `a6dacf4364180d06…` do host — bytes idênticos em dois sistemas
diferentes.

## Opção B — tudo dentro do Docker

Se a máquina não tiver GStreamer, esta é a via mais curta. O Dockerfile já
instala os pacotes certos.

```bash
# A raiz deste repositório é o próprio componente S4
# O modo direto sobe o daemon com o vídeo real montado:
docker build -t s4-media-evidence:test .
docker run --rm -it -p 8080:8080 \
  -v "$PWD/video_test:/app/video_test:ro" \
  s4-media-evidence:test \
  /app/s4_media_evidence --port 8080 \
    --source "/app/video_test/10 Minutes of Amazon Rainforest (Free Download).mp4" \
    --scenario --db /data/s4.db --media-dir /data/media
```

E a verificação automatizada de ponta a ponta:

```bash
./scripts/smoke_e2e.sh ./build/s4_media_evidence
```

> `curl`, `jq` e `sha256sum` são obrigatórios. Sem qualquer um deles o script sai
> com `2` e diz o que falta, porque a conferência do SHA-256 é o item que
> transforma isto em evidência — pular esse item em silêncio daria um `SMOKE OK`
> que não verificou nada. Já `gst-launch-1.0` e um decoder H.264 são opcionais: o
> script marca a etapa como *pula* e segue, deixando explícito na saída que
> verificar container não é verificar pixel.

```
== 1. daemon sobe com replay de arquivo real
  ok    daemon ouvindo em http://127.0.0.1:36483
  ok    cenario extraiu 51184 bytes
  ok    sha256 publicado: a6dacf4364180d06...
== 2. ring buffer alimentado pelo video real
  ok    replay ativo
== 3. o MP4 do cenario e um container real e decodifica
  ok    qtdemux ! h264parse aceitou o container
  ok    assinatura ftyp
== 4. API HTTP
  ok    GET /buffer/stats devolveu 2671 quadros guardados
  ok    POST /events respondeu 201 (clip clip-e9bf0efd-…)
== 5. sha256 publicado bate com o arquivo em disco
  ok    hash do descriptor confere com o arquivo
== 6. a mesma extracao produz o mesmo hash
  ok    hash estavel entre execucoes (a6dacf4364180d06...)

SMOKE OK
```

Se você quer provar o resultado sem abrir o script, o passo 6 sozinho é a
demonstração: **a mesma extração, duas vezes, mesmo hash.**

## Notas operacionais

### `/dev/shm` acumula segmentos se o processo morre

O segmento some corretamente em uma parada limpa — o `close()` faz
`shm_unlink`, e dá para conferir:

```bash
./build/s4_media_evidence --source ... --port 8080 ... &
ls -l /dev/shm/ods_s4_ring_*        # aparece
kill %1                              # encerra com SIGTERM
ls -l /dev/shm/ods_s4_ring_*        # some
```

Se o processo for **abruptamente** morto (`SIGKILL`, `abort()`, OOM killer), o
destrutor não roda e o segmento fica órfão em `/dev/shm`. Como cada segmento
tem o tamanho da janela, execuções repetidas podem encher a tmpfs. Verifique e
limpe:

```bash
ls -l /dev/shm/ods_s4_ring_*
rm -f /dev/shm/ods_s4_ring_*
```

O daemon já se protege disso na subida: `RingBufferConfig.replaceStaleSegment`
(ligado por padrão no `main.cpp`) adota e limpa um segmento deixado pela
execução anterior. Vale notar que isso vale **por câmera** — uma câmera
diferente, como nos testes, usa outro nome de segmento e não é alcançada por
essa limpeza.

### Ports

A porta `8080` é o padrão e conflita: outro processo com algo escutando lá faz
o daemon sair com `cannot bind to port 8080`. Use `--port 0` para o sistema
escolher uma livre (o daemon imprime a que escolheu) — é o que o
`smoke_e2e.sh` faz.

## Referência rápida da API

| Método | Rota | Para quê |
|---|---|---|
| `GET` | `/healthz` | Sonda de saúde do serviço. |
| `GET` | `/api/v1/buffer/stats` | O que o ring buffer tem agora: quadros, bytes, sessão, intervalo do relógio de captura. |
| `POST` | `/api/v1/events` | Dispara um evento e extrai o clipe. `201` com o DTO. |
| `GET` | `/api/v1/clips/{id}` | Descritor do clipe, incluindo o SHA-256. |

### `POST /api/v1/events` — duas formas de pedir a janela

**Por relógio de captura** (o caminho do S4.4; recomendado):

```json
{
  "event_id": "evt-demo-1",
  "capture_ts_ns": 4668598578046,
  "pre_window_seconds": 1.0,
  "post_window_seconds": 0.5
}
```

**Por relógio de parede** (caminho legado, mantido):

```json
{ "event_id": "evt-demo-2", "start_ms": 1720000000000, "end_ms": 1720000001000 }
```

Respostas: `201` criou · `400` janela inválida ou `event_id` com caractere
inválido · `500` janela sem quadros no buffer · `404` clipe inexistente.

## Flags do daemon

| Flag | Padrão | Para quê |
|---|---|---|
| `--port N` | `8080` | Porta HTTP. Use `0` para deixar o sistema escolher (o daemon imprime a escolhida). |
| `--db PATH` | `/tmp/s4_media_evidence.db` | Banco SQLite dos descritores. |
| `--media-dir PATH` | `/tmp/s4_media_evidence` | Onde os clipes são gravados. |
| `--source FILE` | — | Replay de um MP4 H.264 existente, em vez da fonte sintética. **É o que produz um clipe de vídeo real.** |
| `--scenario` | desligado | Na subida, espera o ring buffer ter material e extrai um clipe de demonstração, imprimindo o descritor. Só produz MP4 com `--source`: a fonte sintética alimenta bytes que não são H.264 codificado, e o muxer avisa isso em vez de gravar um arquivo que só parece vídeo. |
| `--camera ID` | `cam0` | Identificador da câmera (vira o nome do segmento em `/dev/shm`). |
| `--window-seconds N` | `30` | Segundos de ring buffer. |
| `--bitrate BPS` | `134400` | Bitrate nominal, usado para dimensionar o ring buffer. |

## Perguntas que aparecem sempre

**"Por que o buffer guardou só 1 900 de 18 032 quadros? Está perdendo vídeo?"**
É o design. O ring buffer é curto e circular de propósito: a garantia é
"tenho os últimos N segundos", não "tenho tudo". A virtualização de
retenção em disco é o S4.3, fora deste escopo. O campo
`frames_evicted_total` existe para que essa conta seja auditável, e não
silenciosa.

**"Por que o mesmo vídeo dá hashes diferentes se eu usar `mp4mux` direto?"**
Porque o `mp4mux` carimba a hora do muxing. Está explicado no Passo 5 e
tratado em `iso_bmff_timestamps.cpp`.

**"Posso desligar essa normalização de timestamp?"**
Sim: `GStreamerMp4Muxer(false)`. Mas aí o hash deixa de ser reprodutível, e
com ele a capacidade de provar que dois artefatos são o mesmo material. Os
campos zerados descrevem *quando o container foi montado*, não *quando o
vídeo foi gravado* — a proveniência do vídeo continua no ring buffer e no
descritor no banco.

**"O relógio de captura e o relógio de parede são a mesma coisa?"**
Não, e a distinção é o que sustenta o S4.2. O relógio de parede pode ser
ajustado por NTP e retroceder; o de captura, não. A conversão entre os dois
acontece em um único ponto. Por isso a janela é pedida em `capture_ts_ns`.

**"Por que o evento não pode ser 'agora'?"**
No replay de arquivo, "agora" não existe depois do fim do stream: os 10
minutos de vídeo são consumidos em ~500 ms e o relógio de captura congela no
fim. Um evento ancorado no instante mais recente pediria um "depois" que
nunca chega, e a extração ficaria esperando até o timeout. Por isso o
instante do evento é sempre derivado do intervalo que o buffer **realmente
guarda** — o que também é o comportamento certo numa câmera ao vivo.

**"Não tenho `openh264enc`. Isso quebra?"**
Não, para este fluxo. `openh264enc`/`openh264dec` servem para *gerar* vídeo
local, e falham neste host. O replay, a demultiplexação, o parse e o remux
não dependem deles. Para gerar um cenário novo, use
`./build/s4_record_scenario` ou um MP4 real.
