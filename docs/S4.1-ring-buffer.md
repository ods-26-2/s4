## 1. O que este submódulo faz (resumo em 1 minuto)

> **Uma frase:** o S4.1 mantém os últimos *N* segundos de vídeo guardados em memória RAM, o tempo todo, para que quando um evento acontecer seja possível recuperar o vídeo **de antes** dele.

Pense em um **gravador de dashcam**: está sempre gravando, mas só guarda os últimos minutos — o vídeo velho vai sendo apagado pelo novo. Quando acontece uma batida, o vídeo dos segundos anteriores **já está lá**.

Aqui o "botão de salvar" não é apertado por uma pessoa: quem aperta é o evento publicado pela camada de inferência (I1–I9), e quem chama é o **S4.2 — Binding Evento-Mídia**.

O professor coloca a exigência de forma direta:

> *"Em torno" é a palavra crítica: exige manter um buffer contínuo dos últimos segundos, para poder gravar o que aconteceu antes de o evento ser detectado. **Não é possível começar a gravar depois da detecção e ainda assim ter o antes.***

**O que o S4.1 NÃO faz:**

| Não faz | Quem faz |
|---|---|
| Gravar `.mp4`, calcular SHA-256, registrar no SQLite | S4.2 — Binding Evento-Mídia |
| Expor a API REST de descritores | S4.4 — API Descritores de Clipe |
| Apagar mídia por LGPD ou cota de disco | S4.3 — Retenção & Expurgo |
| Detectar qualquer coisa na imagem | Camada 2 — I1 a I9 |
| Desenhar vídeo na tela | B6 — OverlayPlayer |

## 2. Entradas, saídas e por onde os dados passam

### 2.1 O que entra

| # | Entrada | De onde vem | Formato |
|---|---|---|---|
| 1 | **Quadros de vídeo** | P4 (câmera CSI) ou P6 (replay), via GStreamer | `CapturedFrame` → H.264 Annex-B, 1 access unit por quadro |
| 2 | **Pedido de trecho** | S4.2, quando chega um evento do barramento | `readWindow(start, end)` ou `extractAround(ts, pre, post)` |
| 3 | **Configuração** | Build da aplicação (P3) | `RingBufferConfig` |

```cpp
struct CapturedFrame {
    Nanoseconds captureTsNs;  // QUANDO o sensor capturou (não quando o software recebeu)
    const std::uint8_t* data; // ONDE estão os bytes (vista, sem cópia)
    std::size_t length;       // QUANTOS bytes
    bool isKeyframe;          // é um I-frame (decodificável sozinho)?
    std::string sessionId;    // de qual sessão de execução/replay veio
};
```

### 2.2 O que sai

| Saída | Para quem | Conteúdo |
|---|---|---|
| `std::vector<std::vector<uint8_t>>` (`readWindow`) | S4.2, via `IMediaBufferReader` | Payloads da janela, começando em keyframe |
| `std::vector<VideoFrame>` (`extractWindow`) | S4.2, via `IRAMBufferFacade` | O mesmo, com timestamp de parede e dimensões |
| `ExtractedSegment` (`extractAround`) | Quem conhece o relógio de captura | Quadros + sessão + **flags de truncamento** |
| `BufferStats` | Observabilidade (B2) | Quadros, span, ocupação, expulsões, rejeições |
| Exceções tipadas | Quem chamou | `WindowNotInBufferError`, `NoDecodableStartError`, … |

### 2.3 Por onde os dados passam

```
┌─────────────────────────────────────────────────────────────────────────────┐
│ CAMADA 1 — P4: câmera CSI (IMX477/IMX519) → ISP → NVENC (H.264)  [hardware] │
└───────────────────────────────┬─────────────────────────────────────────────┘
                                │ GStreamer appsink: 1 buffer = 1 quadro
                                │ (vídeo NUNCA passa pelo broker de eventos)
                                ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ S4.1 — RING BUFFER                                                          │
│   GStreamerAppsinkFrameSource                                               │
│        │  CapturedFrame (ponteiro + tamanho, ainda SEM cópia)               │
│        ▼                                                                    │
│   RingBufferRAMFacade::onFrame()  ── trava o mutex ──┐                      │
│        ├─► RingBuffer::allocate()   decide OFFSET e quem morre   [índice]   │
│        └─► IFrameStore::write()     COPIA os bytes               [arena]    │
│                                  ┌────────────────▼──────────────────────┐  │
│                                  │  /dev/shm/ods_s4_ring_cam0   (RAM)    │  │
│                                  │  ┌───┬─────┬───┬───┬─────┬───┬───┐    │  │
│                                  │  │ P │  I  │ P │ P │  I  │ P │ … │    │  │
│                                  │  └───┴─────┴───┴───┴─────┴───┴───┘    │  │
│                                  └───────────────────────────────────────┘  │
└───────────────────────────────┬─────────────────────────────────────────────┘
                                │ readWindow(start, end) → payloads copiados
                                ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ S4.2 — ExtractClipUseCase: concatena → .mp4 no NVMe → SHA-256 → SQLite      │
│ S4.4 — GET /api/v1/clips/{id} devolve o descritor                          │
└─────────────────────────────────────────────────────────────────────────────┘
                                ▲
                                │ evento JSON (pequeno, com capture_ts)
                    ┌───────────┴────────────┐
                    │ Barramento B3 (Pub/Sub)│ ◄── CAMADA 2: I1..I9 detectam
                    └────────────────────────┘
```

**Duas estradas separadas, e isso é regra do professor:**

* **Estrada do vídeo** (larga, pesada): câmera → GStreamer → memória compartilhada. Nunca toca o broker.
* **Estrada do evento** (estreita, textual): inferência → broker B3 → S4.2. Só JSON; a mídia viaja por referência.

## 3. Exemplo de fluxo completo, passo a passo

Cenário do A3 (Monitoramento, cliente-piloto do ciclo 1): **uma pessoa entra numa zona de risco**; a aplicação quer 15 s antes e 5 s depois.

**Momento 0 — a build sobe (uma vez):**

```cpp
application::RingBufferConfig config;
config.cameraId      = "cam0";
config.windowSeconds = 30.0;      // guarda 30 s de passado
config.bitrateBps    = 4000000;   // o mesmo bitrate que P4 configurou

auto buffer = std::make_shared<infrastructure::RingBufferRAMFacade>(
    config, std::move(fonteGStreamer));
buffer->startCapture("");
```

`config.capacity()` faz a conta `4 Mbps ÷ 8 × 30 s × 1,5` = **22,5 MB**; `SharedMemoryFrameStore` cria `/dev/shm/ods_s4_ring_cam0` com esse tamanho.

**Momentos 1 a 900 — captura contínua (30×/s, para sempre):**

| Quadro | O que acontece |
|---|---|
| nº 1 (keyframe, 60 kB) | `allocate` → offset 0; `write` copia 60 kB para `/dev/shm` |
| nº 2 (delta, 10 kB) | `allocate` → offset 60 000; `write` |
| nº 900 (30 s depois) | a arena encheu: o ponteiro **dá a volta** para o offset 0 |
| nº 901 | escreve no offset 0, **expulsando o quadro nº 1** do índice |

Regime permanente: sempre ~30 s de vídeo, sempre ~22 MB de RAM, nada cresce.

**Momento 901,4 — a inferência detecta o evento** e publica no broker:

```json
{ "event_type": "zone_entry", "zone_id": "risco_prensa_2",
  "capture_ts_ns": 901400000000, "confidence": 0.94 }
```

O S4.2 recebe e chama o S4.1. **Dentro da chamada:**

1. **Monta a janela** — `[886,4 s ; 906,4 s]`.
2. **Espera o futuro chegar** — o buffer só tem até 901,4 s; a thread do chamador **dorme** num `condition_variable` até o quadro de 906,4 s chegar (~5 s reais). No timeout, devolve o que tem com `isTruncatedAtEnd = true`.
3. **Encontra o início decodificável** — 886,4 s cai no meio de um GOP, então recua até o keyframe de **886,0 s**; senão os primeiros quadros sairiam quebrados.
4. **Recorta o índice** — ~612 descritores.
5. **Copia os bytes** — a partir daqui o buffer pode sobrescrever a arena sem corromper o trecho.
6. **Devolve** ~10 MB, sem truncamento.

**Momento 906,5 — o S4.2 assume:** concatena, muxa em `.mp4`, calcula SHA-256, grava no SQLite. O buffer nunca parou de gravar.

## 4. Como o buffer circular funciona por dentro

Duas estruturas trabalham juntas:

**1. A arena (bytes)** — bloco de RAM de tamanho fixo. Burro: só guarda bytes numa posição.
**2. O índice (fichas)** — fila de `FrameDescriptor` em ordem de tempo. Sabe o que existe, onde e de quando.

### 4.1 Escrevendo: o ponteiro que dá a volta

```
Arena de 100 bytes, quadros de tamanhos variáveis:

passo 1:  [ Q1(30) ][ Q2(30) ][ Q3(30) ]....      ponteiro = 90
          índice: Q1, Q2, Q3

passo 2:  chega Q4 com 50 bytes. Não cabe em [90,100).
          → DÁ A VOLTA: escreve em [0,50)
          → Q1 e Q2 ocupavam [0,60) → são EXPULSOS
          [ Q4 (50)          ][ Q3(30) ]....       ponteiro = 50
          índice: Q3, Q4

passo 3:  chega Q5 com 60 bytes. Não cabe em [50,100).
          → DÁ A VOLTA de novo. Q3, sobra da volta anterior, é descartado
            ANTES (senão o índice ficaria fora de ordem por offset)
          → Q4 também sai, porque [0,60) invade sua região
          [ Q5 (60)                   ]....         ponteiro = 60
          índice: Q5
```

Por que **tamanho variável**? Um keyframe H.264 pode ter 60 kB e um quadro P 8 kB; slots fixos dimensionados pelo maior quadro desperdiçariam ~80 % da RAM.

Por que **não dividir** um quadro entre o fim e o começo? Porque assim toda leitura é uma cópia contígua — mais simples e mais rápido, ao custo de alguns bytes ociosos no fim.

**A regra de ouro**, garantida por `allocate()`: *o descritor morre antes de os bytes dele serem sobrescritos*. O teste `nunca_deve_manter_descritor_apontando_para_bytes_sobrescritos` faz 2 000 escritas aleatórias e confere, **a cada passo**, que todo descritor vivo ainda lê o que gravou.

### 4.2 Lendo: por que o trecho começa antes do que você pediu

```
 I₀  P₁  P₂  P₃  P₄  P₅  P₆  P₇  P₈  P₉   I₁₀  P₁₁ ...
 └─ keyframe: imagem completa
     └────── quadros P: só a DIFERENÇA em relação ao anterior
```

Um quadro P sem o keyframe anterior é lixo para o decoder. Então, ao pedir uma janela que começa em P₄:

1. usa o **último keyframe com `ts ≤ início`** (o trecho fica até 1 GOP mais longo, **nunca mais curto**);
2. se esse já foi expulso, usa o **primeiro keyframe dentro da janela**;
3. se não há keyframe, lança `NoDecodableStartError` — melhor falhar com nome do que entregar arquivo quebrado.

## 5. Guia dos blocos: o que cada arquivo faz

### `domain/` — as regras, sem sistema operacional

| Arquivo | Em linguagem simples |
|---|---|
| `value_objects/capture_window.hpp` | `CaptureWindow`: intervalo `[início, fim]` em ns do relógio de **captura**. `around(T, 15, 5)` = "15 s antes até 5 s depois de T". Se for inválido, o objeto nem chega a existir. |
| `value_objects/frame_descriptor.hpp` | `FrameDescriptor`: a "ficha de catálogo" de um quadro — quando, **em que posição da arena** (`offset`), quantos bytes, keyframe?, sessão. É a tupla `(timestamp, pointer, length)` do guia. |
| `value_objects/buffer_capacity.hpp` | A calculadora "quero 30 s a 4 Mbps → 22,5 MB". Ninguém escolhe o tamanho no chute. |
| `value_objects/buffer_segment.hpp` | A resposta de uma consulta: fichas que cobrem a janela + avisos de truncamento. |
| `entities/ring_buffer.hpp/.cpp` | ⭐ **O coração.** Decide onde escrever, quem esquecer e quais fichas respondem a uma janela. Não toca um byte de vídeo. |
| `repositories/frame_store.hpp` | `IFrameStore`: contrato da arena (`write`/`read` por offset). Permite trocar `/dev/shm` por um vetor de teste. |
| `services/frame_source.hpp` | `IFrameSource` + `CapturedFrame`: contrato de "quem me entrega quadros". Câmera, replay e produtor falso usam o **mesmo** contrato. |

| Arquivo | Em linguagem simples |
|---|---|

| `use_cases/extract_capture_window.hpp` | Pergunta ao índice quais fichas cobrem a janela e busca os bytes de cada uma. |
| `dtos/extracted_segment.hpp` | O pacote entregue ao S4.2, com bytes próprios. `asElementaryStream()` concatena num H.264 pronto para o muxer. |
| `ring_buffer_config.hpp` | Os parâmetros da build: câmera, segundos, bitrate, dimensões. |

## 6. Decisões de projeto e o porquê

### 6.1 Guardar H.264 comprimido, não quadros crus

| Formato | 1080p30, 30 s | Cabe na Orin Nano (8 GB compartilhados)? |
|---|---|---|
| RAW NV12 | **~2,7 GB** por câmera | Não — deixaria a GPU sem memória para I1/I4 |
| H.264 4 Mbps (+50 %) | **~21 MB** por câmera | Sim, com folga |

~130× menos bytes, e o clipe final é H.264 de qualquer jeito.

### 6.2 Memória compartilhada POSIX (`/dev/shm`)

1. **Zero desgaste do NVMe** — `tmpfs` é 100 % RAM.
2. **Visível a outros processos** — se o S4.2 rodar em processo separado, mapeia o mesmo segmento e lê pelo `offset`, sem cópia extra. Por isso o descritor guarda offset, não ponteiro.
3. **É o mesmo mecanismo** que o `shmsink`/`shmsrc` de P4 já usa.

> **Docker:** o padrão é 64 MB de `/dev/shm`. O `docker-compose.yml` define `shm_size: 256m`.

### 6.3 Pipeline GStreamer: o que está fixado e por quê

| Propriedade | Motivo |
|---|---|
| `insert-sps-pps=true` + `h264parse config-interval=-1` | Repete SPS/PPS em **todo** keyframe. Sem isso, um trecho que começa no meio do stream não decodifica. |
| `stream-format=byte-stream, alignment=au` | Annex-B, um access unit por buffer: concatenar dá um `.h264` válido e nenhum buffer traz "meio quadro". |
| `iframeinterval=30` / `key-int-max=30` | Um keyframe por segundo limita o recuo de alinhamento a ≤ 1 s. |
| `appsink sync=false drop=false` | Não é player; e não descarta quadro em silêncio — prefere backpressure, que aparece nas métricas. |

### 6.4 Dois relógios, uma ponte

P4 é categórico: o quadro sai "carimbado com o instante em que foi capturado, não com o instante em que o software o recebeu". Esse relógio é **monotônico** (não retrocede). Já o S4.2 e a API REST trabalham em `system_clock` (relógio de parede, que o NTP pode ajustar para trás).

`CaptureClockBridge` ancora, no primeiro quadro de cada sessão, o par *(parede agora, captureTs daquele quadro)*; daí em diante a conversão é uma soma. **Ancorar por sessão** é o que faz o replay de P6 funcionar. Quando TRA-1/TRA-2 publicarem a base de tempo oficial de B2, é essa classe que muda — nada mais.

Timestamp que retrocede **dentro** da mesma sessão é rejeitado (`NonMonotonicTimestampError`) e contado em `framesRejectedTotal`: B2 diz que o relógio "nunca retrocede silenciosamente", e a rejeição contabilizada é o "não silenciosamente".

**Por que o carimbo usa o DTS (quando existe):** o buffer guarda os quadros em **ordem de decodificação**, que é a ordem em que o appsink os entrega e a única em que a concatenação forma um H.264 válido. Com B-frames — comuns em `.mp4` de replay, como o de `video_test/` — o PTS sai fora dessa ordem (`I P B B …`: 0,033 s → 0,133 s → 0,067 s) e cada B-frame seria rejeitado como "relógio voltando". Sem B-frames, que é o caso do NVENC de P4, DTS e PTS coincidem e o valor continua sendo o instante de captura.

### 6.5 Esperar o "depois" do evento

No instante do evento o "antes" já está no buffer, mas o "depois" ainda está sendo capturado. `extractAround(..., waitTimeoutSeconds)` bloqueia num `condition_variable` até alcançar `T + post`; no timeout devolve o que existe com `isTruncatedAtEnd = true`. O chamador nunca precisa fazer *polling*.

### 6.6 Copiar os bytes na extração

`ExtractedFrame` é **dono** dos seus bytes. Custa uma cópia (~10 MB, poucos ms), mas garante que o buffer pode continuar sobrescrevendo a arena enquanto o S4.2 codifica.

### 6.7 Um buffer por câmera, por build

`cameraId` gera `/dev/shm/ods_s4_ring_<cameraId>`. A build de A3 com duas câmeras instancia dois buffers; nada é compartilhado entre aplicações — como manda o manual do professor.

### 6.8 Segmento órfão

Se um processo morre sem liberar o `/dev/shm`, o arquivo fica para trás e a criação exclusiva do próximo falha. Por isso existe `RingBufferConfig::replaceStaleSegment`: **desligado por padrão** (duas instâncias da mesma câmera não se sobrescrevem em silêncio) e **ligado no daemon**, onde reiniciar após uma queda é o comportamento correto.

## 7. Dimensionamento: quanta RAM por câmera

| Perfil | 15 s | 30 s | 60 s |
|---|---|---|---|
| H.264 720p 2 Mbps | 5 MB | 11 MB | 21 MB |
| H.264 1080p 4 Mbps | 11 MB | **21 MB** | 43 MB |
| H.264 1080p 8 Mbps | 21 MB | 43 MB | 86 MB |
| RAW NV12 1080p30 | 1 335 MB | 2 670 MB | 5 339 MB |

**Recomendação:** `windowSeconds = 30` a 1080p/4 Mbps custa ~21 MB por câmera — duas câmeras = 42 MB, menos de 1 % da RAM da Orin Nano. O limite prático não é a RAM: é o maior `preSeconds` que alguma aplicação da build vai pedir.

> **Regra:** `windowSeconds ≥ max(preSeconds) + duração do GOP`, porque o alinhamento a keyframe pode recuar até um GOP inteiro.

## 8. Como usar (S4.2 e builds de aplicação)

```cpp
#include "s4/infrastructure/gstreamer/appsink_frame_source.hpp"
#include "s4/infrastructure/gstreamer/ring_buffer_ram_facade.hpp"

using namespace ods::s4;

// 1) montagem — na Jetson, com a câmera CSI
application::RingBufferConfig config;
config.cameraId      = "cam0";
config.windowSeconds = 30.0;
config.bitrateBps    = 4000000;

infrastructure::CsiCameraOptions camera;
camera.bitrateBps = config.bitrateBps;

auto buffer = std::make_shared<infrastructure::RingBufferRAMFacade>(
    config,
    std::make_unique<infrastructure::GStreamerAppsinkFrameSource>(
        infrastructure::GStreamerAppsinkFrameSource::jetsonCsiH264Pipeline(camera),
        "exec-2026-09-22-001"));

buffer->startCapture("");

// 2) o S4.2 não precisa saber de nada disso: só da porta
application::ExtractClipUseCase useCase(repository, buffer, fileStorage);
const auto clip = useCase.execute(eventId, domain::TimeWindow(start, end), path);

// 3) quem conhece o relógio de captura pode usar a API nativa
const auto segment = buffer->extractAround(evento.captureTsNs, 15.0, 5.0, 8.0);
segment.asElementaryStream();      // H.264 Annex-B, começa em keyframe
segment.isTruncatedAtStart;        // o "antes" veio completo?
segment.isTruncatedAtEnd;          // e o "depois"?

buffer->stats();                   // framesStored, spanSeconds(), fillRatio()…
buffer->stopCapture();             // para a fonte e remove o /dev/shm
```

Trocar a fonte é a única mudança entre ambientes: `SyntheticFrameSource` (sem hardware), `RecordedFrameSource` (cenário gravado) ou `GStreamerAppsinkFrameSource` (câmera, `shmsrc` de P4 ou replay de arquivo).

## 11. Limitações conhecidas e próximos passos

* **Snapshot (`.jpg`)** — o buffer guarda H.264; um snapshot exige decodificar o keyframe mais próximo. Próximo passo: `extractKeyframeAt(ts)` + decodificação no S4.2 (`nvv4l2decoder`/`nvjpegenc`).
* **Áudio (P5)** — fora do escopo do S4.1; a arquitetura comporta um segundo buffer com o mesmo `IFrameSource`, alinhado pelo `captureTs`.
* **Medição na placa** — os números da seção 7 são calculados; falta medir na Jetson o consumo real com NVENC e a latência do callback a 30 fps.
* **Índice em outro processo** — a arena é compartilhável, mas o índice ainda vive no processo do buffer. Se o S4.2 rodar separado, o índice precisa ir para o segmento (cabeçalho fixo + sequência atômica).
* **Uma câmera por instância** — múltiplas câmeras exigem um agregador (`map<cameraId, RingBufferRAMFacade>`).
* **Hardware** — o caminho GStreamer → NVENC → câmera CSI só pode ser validado na própria Jetson.
